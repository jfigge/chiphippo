# AI circuit generation — audit

An audit of the AI circuit-generation feature (toolbar **AI** segment → AI panel in
**Build** mode), dated 2026-09-27. Line numbers are against the working tree on
`main` at `5573cda`, including uncommitted changes (`src/app/main.js`,
`src/app/preload.js` and `src/web/scripts/sim/engine.js` carry working-tree edits,
none of them in the code paths cited here).

**Method.** I read the code paths below. Where a finding says **(probe)**, I also
confirmed it by running the real modules (`compileNetlist`, `verifyBuild`,
`buildStepsFromReply`, `resolvePin`, `buildRepairMessage`) under `node` against
hand-written specs. Those probe scripts were throwaway and are not in the repository.
The probes made no network calls.

Unless a path starts with `src/`, it is relative to `src/web/scripts/`.

## 1. Component inventory

### Where definitions live

- **No part is defined in a data file** — nowhere is there JSON, YAML or CSV. Every part
  definition is a JavaScript object literal in an ES module under `catalog/`, built
  with the helpers in `catalog/pin-builders.js:24-42` (`pin`, `input`, `output`, `io`,
  `nc`, `gnd`, `vcc`, `unit`, `buf3`).
- `catalog/index.js` collects the modules. `CHIP_DEFS` is at `:65`: it stamps
  `kind: "chip"` and a `normalizeParams`. `PALETTE_DEFS` (`:95`) is
  `[...CHIP_DEFS, ...PART_DEFS]`, with 83 entries. Lookup goes through `chipDef`
  (`:101`) and `partDef` (`:106`).
- **Pin-outs are always data**: the `pins: [{n, name, role}]` array on each def. Roles
  are `input`, `output`, `io`, `nc`, `gnd` and `vcc`; discretes also use `contact`,
  `anode`, `cathode`, etc. Bricks (`psu`, `clock`) have `terminals` rather than pins.
- **Behaviour lives in one of five places:**
  1. **Pure data**: `logic.units` holding gate primitives, e.g. `unit("NAND", [1, 2], 3)`
     (`catalog/chips-gates.js:55`). The generic `evaluate` (`sim/chip-eval.js:102`)
     interprets these through `sim/levels.js:50-95` (`and`, `or`, `nand`, `nor`, `xor`,
     `inv`, `buf3`).
  2. **COMB units**: code wrapped in data. A builder in `sim/sequential.js` returns
     `logic.units` entries that carry a `compute` function (e.g. `decoderUnits`
     `:365`). `evaluate` walks them.
  3. **Sequential builders**: code. `sim/sequential.js` returns
     `{state0, step, outputs}`, e.g. `seqChip` `:60`, `dffUnit` `:101`, `jkUnit`
     `:121`.
  4. **Per-part cores**: code. CPUs, peripherals and the LCD controller each have their
     own module (`sim/w65c02.js`, `sim/z80.js` + `sim/z80-ops.js`, `sim/w65c21.js`,
     `sim/w65c22.js`, `sim/hd44780.js`) behind the same sequential contract.
  5. **Discretes**: an `internalBridges(params, state)` function on the def. It feeds
     only the netlist and does no logic evaluation. LED burn/lit is physics in
     `sim/junction.js:61` (`junctionState`) and `:77` (`isLit`).

None of the following can be expressed in the AI output contract. The compiler emits
the first three itself.

  at `MAX_ELEMENTS` (`model/integration.js:79`).

### What the AI can actually use

The system prompt lists all 83 `PALETTE_DEFS`. The compiler refuses two of them:
`osc-full` and `osc-half` carry `can`, which raises `UNSUPPORTED_PART` at
`model/autobuild.js:220-230`. The compiler always plants its own 5 V PSU
(`model/autobuild.js:993`), and the model is told never to list power pins.

## 2. The request path

### Flow, from typed request to placed circuit

1. **Send.** `AiPanel#onSend` (`components/ai-panel.js:622-664`) resets `#repairs`
   (`:655`), pushes `{role: "user", content: prompt}` onto `#history`, and calls
   `#request`. `#history` is a running conversation: only **Clear** (`:525`) or a mode
   switch (`:372`) resets it, so a follow-up prompt continues the previous design
   thread.
2. **Request.** `#request` (`:769`) calls
   `window.chiphippo.ai.start({...config}, buildSystemPrompt(), this.#history, undefined)`
   (`:789-795`). The config is `currentSettings.ai`, wired at `app.js:1514`.
3. **Bridge.** `src/app/preload.js:182-195` invokes `ai:start`. The streamed replies
   come back as `ai:delta` / `ai:done` pushes, re-dispatched as `chiphippo:ai-delta` /
   `chiphippo:ai-done` (`src/app/preload.js:85-86`). The panel listens for them at
   `components/ai-panel.js:224-229`.
4. **Main.** The `ai:start` handler (`src/app/main.js:2015-2036`) reads the key
   (`:2019`) and calls `aiClient.start`. Deltas are pushed as `ai:delta`, and the
   result as `ai:done`.
5. **HTTP.** `start` (`src/app/ai/client.js:107-203`) builds the provider request
   (`:141-152`), `fetch`es it (`:153-158`), and reads SSE with `readSSE` (`:48-72`). A
   non-2xx response goes through `describeStatus` (`:75-88`). A refusal returns
   `ok:false` (`:182`), and so does an empty body (`:183-185`).
6. **Build.** `#onDone` (`components/ai-panel.js:848`) hands the text to `#build`
   (`:905-940`), which steps `buildStepsFromReply` (`ai/generate.js:246-251`) through
   four stages:
   - `parseNetlist` (`ai/generate.js:119-154`)
   - `compileNetlist` (`model/autobuild.js:136-140`)
   - `verifySteps` (`model/autobuild-verify.js:122`)
   - `designClipOf` on the *verified* document (`ai/generate.js:201`;
     `model/autobuild.js:1664-1672`)
7. **Accept.** `#consume` (`components/ai-panel.js:943`) → `#accept` (`:988-1017`) →
   `this.#onDesign(built.clip)` (`:1017`) → `controller.armGeneratedDesign(clip)`
   (`app.js:1524`; `components/desk-controller.js:949-951`) →
   `DeskPlacement.armGeneratedDesign` (`components/desk-placement.js:737-742`). This
   arms a cursor-following ghost.
8. **Place.** A click commits through `#dropDesign` (`components/desk-placement.js:680-722`)
   into `DeskDoc.pasteDesign` (`model/desk-doc.js:3401`). That is one all-or-nothing
   transaction and one undo step. `applyGeneratedDesign`
   (`components/desk-placement.js:753-763`) drops the design without a ghost; the
   panel does not use it.

### The system prompt

- It is built in `ai/catalog-brief.js`: `buildSystemPrompt()` (`:225-227`) returns
  `RULES` (`:97-217`) followed by `buildCatalogCard()` (`:73-86`). It is about
  18,400 characters and 230 lines (probe).
- `RULES` has these sections:
  - the role (`:98-103`)
  - the JSON format with an example (`:105-126`)
  - rules the compiler enforces (`:128-161`)
  - how to write `notes` (`:163-181`)
  - how to write `tests` (`:183-195`)
  - output instructions (`:197-201`)
  - the catalog legend (`:203-216`)
- The prompt is sent as a system block with `cache_control: {type: "ephemeral"}`
  (`src/app/ai/providers.js:224`), so the repair rounds re-read it from cache.
- **Review mode** (Feature 320) shares the transport but uses a different prompt,
  `buildReviewSystemPrompt` (`ai/catalog-brief.js:299`), and a prose answer
  (`opts.format: "prose"` → `schema: null`, `src/app/main.js:2021`). It does not
  generate circuits.

### Component information injected into the prompt

`buildCatalogCard` (`ai/catalog-brief.js:73-86`) writes one line per `PALETTE_DEF`,
grouped by `def.group`. `partLine` (`:62-70`) formats each line as
`id [package] — title. n:name<mark> …`. The mark comes from `pinMark` (`:55-60`):
`!` for an `outputEnable` pin, `>` for `role === "output"`, `<>` for `io`, and nothing
otherwise. Verbatim sample (probe):

```
74LS74 [DIP-14] — Dual D flip-flop, preset & clear. 1:1CLR 2:1D 3:1CLK 4:1PRE 5:1Q> 6:1Q̄> 7:GND 8:2Q̄> 9:2Q> 10:2PRE 11:2CLK 12:2D 13:2CLR 14:VCC
74LS244 [DIP-20] — Octal buffer/line driver, tri-state. 1:1G! 2:1A1 3:2Y4> … 19:2G! 20:VCC
AT28C256 [DIP-28] — 32K×8 EEPROM. 1:A14 … 11:DQ0<> … 20:CE 21:A10 22:OE … 27:WE 28:VCC
clock — Clock source. out gnd
```

**Not injected**:

- behaviour or truth tables
- the `blurb`
- `pinGroups`, so the resolver's `NAME[i]` bus syntax (`model/pin-resolve.js:191-212`)
  is undocumented to the model
- which unmarked pins are power, contacts, anodes or cathodes. The legend says
  `(none)  an input` (`ai/catalog-brief.js:207`), yet `GND`, `VCC`, switch contacts and
  LED anodes/cathodes are all unmarked.
- that a memory device's `CE`/`OE`/`WE` are active-low

## 3. Output contract

**Structured JSON, schema-constrained at the provider, then parsed tolerantly.** The
model returns a coordinate-free netlist. It never emits holes, columns, anchors or
wires (`ai/catalog-brief.js:100-103`).

### The schema

`NETLIST_SCHEMA` (`src/app/ai/providers.js:84-134`) is shared by both adapters:

```js
{
  type: "object",
  properties: {
    title: optional({ type: "string" }),
    notes: optional({ type: "string" }),
    parts: { type: "array", items: { type: "object",
      properties: { id: { type: "string" }, ref: { type: "string" },
                    label: optional({ type: "string" }) },
      required: ["id", "ref", "label"], additionalProperties: false } },
    nets: { type: "array", items: { type: "object",
      properties: { name: { type: "string" },
                    members: { type: "array", items: { type: "string" } } },
      required: ["name", "members"], additionalProperties: false } },
    tests: optional({ type: "array", items: { type: "object",
      properties: { name: { type: "string" }, set: optional(PIN_MAP),
                    edges: optional({ type: "integer" }), expect: PIN_MAP },
      required: ["name", "set", "edges", "expect"], additionalProperties: false } }),
  },
  required: ["title", "notes", "parts", "nets", "tests"],
  additionalProperties: false,
}
```

- `PIN_MAP` (`:45-56`) is `[{target: string, value: string}]`.
- `optional(s)` (`:68-69`) is `{anyOf: [s, {type: "null"}]}`, because strict mode
  cannot omit keys.

The schema constrains **shape only**:

- `ref` is a free string, not an enum of catalog ids.
- Net `members` are free strings.
- There are no length or count constraints.
- `tests` may be `null`.

Server-side enforcement depends on the provider; a local OpenAI-compatible server may
ignore `response_format` (see `ai/generate.js:45-47`).

### Member grammar

A net member is either a rail token or `<partId>.<pin>`. `parseMember` is at
`model/pin-resolve.js:83-98`, and the rail tokens `VCC`, `+`, `VDD`, `GND`, `-`, `VSS`
are at `:45-52`. A net *named* `VCC`/`GND` also binds to that rail
(`model/autobuild.js:262`).

A pin token goes through `resolvePin` (`model/pin-resolve.js:109-219`), which tries
these rungs in order:

| Rung | Match | Lines |
|---|---|---|
| ⓪ | `#n` (explicit pin number) | `:125-133` |
| ① | bare integer as pin number; reports `AMBIGUOUS_PIN` if a pin is *named* that integer | `:142-161` |
| ② | exact, case-sensitive name | `:166-167` |
| ③ | power role (`VCC`/`GND`/`VDD`/`VSS`) | `:171-175` |
| ④ | case-insensitive name | `:181-184` |
| ⑤ | punctuation-stripped, upper-cased name | `:187-189` |
| ⑥ | `NAME[i]` against `pinGroups` | `:193-212` |
| — | otherwise `UNKNOWN_PIN` with candidates | `:216-218` |

When more than one pin matches, `oneOf` (`:229-246`) returns the lowest pin number if
they all share a role, and `AMBIGUOUS_PIN` if their roles differ.

### Parsing

- `parseNetlist` (`ai/generate.js:119-154`) takes the contents of a ```` ```json ````
  fence if one is present. Otherwise it slices from the first `{` to the last `}`,
  then runs `JSON.parse`. Failure yields `NOT_JSON` (`:131`, `:148`).
- `dropNulls` (`:78-87`) removes every null-valued key.
- `foldPinMaps` (`:90-106`) with `pinMap` (`:53-66`) turns each test's `[{target, value}]`
  into `{target: value}`, stringifying values. It also accepts an already-map-shaped
  object from a server that ignored the schema.

### The four specific questions

- **Pin direction — partially.**
  - `MULTIPLE_DRIVERS` counts only `role === "output"` pins (`model/autobuild.js:338-343`).
    `io` pins are not counted.
  - Tri-state outputs *are* counted, so two '244/'125 outputs on one bus net are
    refused even with correct enables (probe: `MULTIPLE_DRIVERS … ties 2 outputs
    together (U1.3, U1.6)`).
  - An output pin in a `VCC`/`GND` net passes every gate (see gap 4).
  - An input-only net is caught at run time by L6, but only for **declared** nets.
    Input pins the spec never mentions are not checked at all (see gap 3).
  - The card's `>`/`<>`/`!` marks are the model's only view of direction
    (`ai/catalog-brief.js:55-60`).
- **Power/ground pins — yes.**
  - Listing one is `POWER_PIN_LISTED` (`model/autobuild.js:300-316`).
  - Power is derived from `role: "vcc"|"gnd"` and wired by the compiler, with a PSU
    planted at `volts: 5` (`:993`).
  - A net joining the rails is `NET_SHORTS_RAILS` (`:333-336`).
  - A chip whose power status is not ok is `CHIP_NOT_OK` / `SIM_UNDERPOWERED` at L5.
- **Bus widths — only for index syntax.**
  - `NAME[i]` is range-checked against the def's `pinGroups`
    (`BUS_INDEX_OUT_OF_RANGE`, `model/pin-resolve.js:204-210`).
  - The spec has no bus or width concept.
  - Test bit strings are **not** width-checked: `bitsOf` (`model/autobuild-verify.js:545-556`)
    reads the first `width` characters and treats missing ones as `0` (see gap 5).
- **Part-number existence — yes, at compile time.** `UNKNOWN_REF` via `partDef`
  (`model/autobuild.js:212-218`; also `model/pin-resolve.js:111`). The schema does not
  enforce it, because `ref` is a free string. The two oscillators exist in the catalog
  and prompt but are refused (`UNSUPPORTED_PART`).

## 5. Error feedback loop

**Yes: repair-class faults go back to the model, up to 2 extra rounds.** Each send
therefore makes at most **3 requests**: the first plus `MAX_REPAIRS = 2`
(`components/ai-panel.js:77`).

`#consume` (`components/ai-panel.js:943-986`) runs this logic:

1. `partitionFaults` (`ai/generate.js:254-261`) splits the faults. **abort** means
   `kind === "abort"`; **repair** is everything else, including `NOT_JSON`, which has
   no `kind`.
2. **Any abort fault** → the panel shows `ai.compilerFault` with the codes. Nothing is
   sent back (`:952-964`).
3. **Repair faults with `#repairs >= 2`** → the panel shows `ai.gaveUp` and stops
   (`:966-975`).
4. **Otherwise** → `#repairs += 1` (`:977`). The panel pushes the model's reply as an
   `assistant` turn and `buildRepairMessage(repair)` as a `user` turn (`:983-984`), then
   calls `#request()` again. The whole conversation is re-sent with the same (cached)
   system prompt.

Transport failures are **not** retried: HTTP errors, refusals, empty replies and
cancellation (`#onDone`, `:863-869`). The counter resets on each send (`:655`), on
Clear (`:530`) and on a mode switch (`:373`).

### What is sent back

`buildRepairMessage` (`ai/catalog-brief.js:315-327`):

```js
export function buildRepairMessage(faults) {
  const lines = faults.map((f) => {
    const where = f.path ? ` at ${f.path}` : "";
    const extra = f.candidates ? ` (candidates: ${f.candidates.join(", ")})` : "";
    return `- ${f.code}${where}: ${f.message}${extra}`;
  });
  return (
    `That netlist did not pass. Fix exactly these and return the whole ` +
    `corrected JSON object:\n${lines.join("\n")}`
  );
}
```

Only `code`, `path`, `message` and `candidates` are sent. Compiler warnings and
passing test results are not.

### Representative messages (probe, exact output)

A compile-stage round. The spec put two '125 outputs on one net, misnamed the enable,
and listed a VCC pin:

```
That netlist did not pass. Fix exactly these and return the whole corrected JSON object:
- MULTIPLE_DRIVERS at nets[0]: Net "BUS" ties 2 outputs together (U1.3, U1.6).
- UNKNOWN_PIN at nets[1].members[0]: "74LS125" has no pin named "1OE". (candidates: 1G, 1A, 1Y, 2G, 2A, 2Y, GND, 3Y, 3A, 3G, 4Y, 4A, 4G, VCC)
- POWER_PIN_LISTED at nets[2].members[0]: "U2.VCC" is 74LS74's VCC pin. The compiler wires power itself — drop it from net "PWR".
```

A run-time round. The spec omitted the '244's enables:

```
That netlist did not pass. Fix exactly these and return the whole corrected JSON object:
- OUTPUTS_DISABLED: Net "OUT" floats because c2 (74LS244)'s outputs are switched off: its active-LOW output enables 1G (pin 1) and 2G (pin 19) are not wired at all. Tie them to GND.
- TEST_FAILED: switch on: D reads 00000000, expected 10000000
```

In the second message the chip is named **`c2`**, the compiler's re-minted component
id (`model/autobuild.js:1105`), not the spec's `U2`. L3–L6 faults carry desk ids; only
compile-stage faults carry a spec `path`.

A single inverter fed back to itself gives:

```
- UNSETTLED: The circuit never reached a stable state.
- SIM_OSCILLATION: oscillation
- NET_NOT_DRIVEN: Net "LOOP" settles to X — nothing drives it.
```

The oscillation carries no location. `describeWarning` (`model/autobuild-verify.js:397-400`)
reads `w.chip ?? w.net`, but an oscillation warning carries `nets`. The oscillating net
is then also reported as "nothing drives it".

## 6. Gaps

Ranked by how likely each is to produce a **silently wrong circuit**, meaning one that
passes every gate and is placed on the desk. The fixes are left to the reader.

1. **Pin-name normalisation resolves near-miss spellings to a different pin, with no
   error.**
   - *Mechanism.* Rung ⑤ (`model/pin-resolve.js:186-189`) strips every non-alphanumeric
     character, which includes the combining macron in `1Q̄`. `oneOf` (`:229-246`) then
     treats same-role matches as interchangeable and returns the lowest pin number. The
     header comment (`:33-35`) says only `NC`/`VSS` are ever duplicated; that holds for
     exact names, not for normalised ones.
   - *Scale.* The catalog has **26 same-role collisions across 10 chips** (probe):
     '73, '74, '75, '76, '107, '112, '165, '175 (`nQ` vs `nQ̄`), '85 (`A>B`/`A=B`/`A<B`
     and `IA<B`/`IA=B`/`IA>B`), and '595 (`QH` vs `QH'`).
   - *Examples (probe).*
     - `74LS74` with `1Q'`, `/1Q`, `~1Q` or `1Q̅` (combining overline U+0305) → pin 5
       (`1Q`, the true output).
     - `74LS595` with `QH’` (curly apostrophe) → pin 7 (`QH`), not pin 9 (`QH'`).
     - `74LS85` with `A>=B` → pin 5 (`A>B`); `IA_B` → pin 2 (`IA<B`).
     - Whether the result lands on the inverted or true output depends only on pin
       numbering: '75 `1Q̄` is pin 1, below `1Q` at pin 16.
   - *End to end.* A `74LS74` spec using `U1.1Q'` compiled and verified `ok: true`
     (probe).
   - *Test coverage.* The compiler corpus addresses every pin as `#n`
     (`tests/autobuild-corpus.test.js`), so it never exercises this path.
     `tests/pin-resolve.test.js` has no case for it.
2. **L7 is the only check of intent, and it is optional and self-authored.**
   - `tests` may be `null` (`src/app/ai/providers.js:117-130`); `dropNulls` removes it,
     and `runFunctionalTestSteps` then returns `[]` (`model/autobuild-verify.js:514`).
   - The prompt asks for "at least two" (`ai/catalog-brief.js:188`), but nothing
     enforces a minimum. A no-test build is accepted, and the summary simply omits the
     test count (`components/ai-panel.js:998`).
   - The same model writes the circuit and its tests, so a misunderstanding of the
     request passes as long as the two agree.
   - L5 and L6 test a single state: switches as placed, clocks idle-low
     (`model/autobuild-verify.js:298-301`). Everything else is L7's alone.
3. **Input pins absent from the netlist float HIGH, and nothing reports it.**
   - L6 iterates only `compiled.nets` (`model/autobuild-verify.js:343-372`), and nothing
     enumerates a part's unlisted inputs.
   - The prompt says "Do not leave a used input floating" (`ai/catalog-brief.js:137`)
     but nothing checks it.
   - *Probe.* A `74LS138` with `G2A`/`G2B`/`B`/`C` omitted verifies clean with no tests.
     `G2A` reads HIGH, so the decoder is disabled and every output sits HIGH.
4. **An output tied directly to a rail passes every gate.**
   - `MULTIPLE_DRIVERS` needs two `output` pins (`model/autobuild.js:338-343`).
   - The engine gives a supply precedence over a chip output with no warning
     (`sim/resolve.js:53-54`).
   - L6 skips rail nets (`model/autobuild-verify.js:344`).
   - *Probe.* `{name: "GND", members: ["U1.1Y", "U1.1A"]}` on a `74LS00` → `ok: true`,
     no faults.
5. **Test bit strings are not width-checked.**
   - `bitsOf` (`model/autobuild-verify.js:545-556`) pads a short string with `0` and
     ignores the excess.
   - For a switch bank, the width is `pins.length / 2` (`:570`); for a display it is
     `segments.length` (`:657`).
   - *Probe.* `set: {SW: "1"}` on an 8-position bank with `expect: {D: "0"}`, and a
     13-character set with a 16-character expect, both pass.
   - A short `expect` string therefore silently asserts that the remaining segments are
     unlit, and a short `set` string silently opens the remaining switches.
6. **`edges` is silently ignored when the design has no `clock` part.**
   `runOne` clocks only when `edges > 0 && clocks.length` (`model/autobuild-verify.js:587`).
   Otherwise it does a plain `settle` and compares, and never says the edges were not
   applied. A sequential test can pass against the power-on state.
7. **Isolated-segment displays burn without a report.**
   - `commonLeg` returns `null` for `bar8iso`, which has no shared anode or cathode
     (`model/autobuild.js:706-721`), so no series resistor is interposed.
   - A burnt junction is not an engine warning; only `isLit` in an L7 display
     expectation sees it (`model/autobuild-verify.js:658-676`).
   - *Probe.* Output → `A1`, `K1` → `GND`, no tests → `ok: true`. With a test expecting
     segment 1 lit → `TEST_FAILED … reads 00000000`.
8. **Bidirectional (`io`) pins are outside the driver check.** Contention between two
   `io` pins, or between `io` and `output`, is caught only if both drive in the single
   default-state settle (L5 `SIM_CONFLICT`) or in a test. The affected pins are the
   memory `DQ` and CPU/PIA/VIA data buses.
9. **Fault messages can steer a repair toward a different wrong circuit.**
   - L3–L6 faults name compiler ids (`c2`) and net ids, not spec ids (§5). With two
     identical parts, the model cannot tell which one is meant.
   - `SIM_*` warnings carry the type alone.
   - An oscillating (`X`) net is reported as "nothing drives it"
     (`model/autobuild-verify.js:348`, `:366`).
   - The compiler's own insertions (`RESISTOR_INSERTED`, `PULL_INSERTED`) are never
     shown to the model, so it cannot reason about them.
10. **Memory contents cannot be specified.** `NETLIST_SCHEMA` has no field for ROM or
    EEPROM bytes (`src/app/ai/providers.js:84-134`). A generated design containing a
    ROM has no program.

### Weaknesses that fail loudly rather than silently

These cost rounds or refuse valid designs; they do not produce wrong circuits.

- **Tri-state buses are unrepresentable.** `MULTIPLE_DRIVERS` refuses two tri-state
  outputs on one net, yet the prompt's `!` legend allows "the design genuinely takes
  the part off a shared bus" (`ai/catalog-brief.js:214`).
- **The oscillators are offered but refused.** `osc-full` and `osc-half` appear in the
  catalog card, and the compiler rejects them (`UNSUPPORTED_PART`).
- **The prompt and the compiler disagree about bare LEDs and resistors.** The prompt
  says a bare `led`/`resistor` "cannot be expressed" (`ai/catalog-brief.js:159`), but
  the compiler accepts a `led` and interposes its resistor (probe: `RESISTOR_INSERTED`,
  `ok: true`).
- **Memory enables get the wrong diagnosis.** Memory `CE`/`OE`/`WE` carry no `!` mark
  and no `outputEnable`, so a floating memory output is reported as `NET_NOT_DRIVEN`
  rather than `OUTPUTS_DISABLED`.
- **Test pin names use a narrower lookup.** Pins inside `expect` are matched by exact
  name or number only (`model/autobuild-verify.js:634-637`), not through `resolvePin`.
  A name that compiles in a net can therefore fail in a test (`TEST_FAILED … has no pin`).
- **Abort-class faults are never retried**, by design, and neither are transport
  failures.
- **A cited test file does not exist.** `ai/catalog-brief.js:93-95` says the prompt is

## Follow-up — fixes made after this audit (2026-09-27)

Everything above describes the code as it was audited. The line numbers
reflect that version, and several of the files it cites have changed since.
Each gap below was then addressed and covered by tests; `make test` passes.

| # | Gap | What changed |
|---|---|---|
| 1 | Near-miss pin names resolved to a different pin | `model/pin-resolve.js` now keeps the notation that carries meaning (`canonical`). An overbar, a leading `/` or `~`, or a trailing `'` marks a complement; `>`, `<` and `=` name different pins. A loose match landing on two different names is `AMBIGUOUS_PIN` (`oneName`). A marked token is refused on an unmarked OUTPUT (`1Q'` on the '174). `tests/pin-resolve.test.js` sweeps the whole catalog: no respelling may land on a different pin. |
| 2 | Tests optional and unenforced | `ai/generate.js` `testSuiteFaults` requires at least `MIN_TESTS` (2, quoted in the prompt) and rejects two tests with identical inputs (`TOO_FEW_TESTS`, `DUPLICATE_TEST`). A test must expect something. Self-authorship remains; see below. |
| 3 | Unlisted inputs floated silently | New `model/spec-lint.js` `floatingInputs` runs at L6 as `INPUT_FLOATING`. A unit whose output is used needs all its inputs. Parts without units are read by their `1…`/`2…` section numbering, and shared inputs are needed once any output is used. |
| 4 | Output on a rail passed | `OUTPUT_ON_RAIL` is raised in `resolveSpec` (`model/autobuild.js`). |
| 5 | Bit strings not width-checked | `bitsOf` requires exactly the part's width; anything else is `TEST_INVALID`. |
| 6 | `edges` without a clock ignored | Now `TEST_INVALID`. Each test also starts from the as-built switch positions, not the previous test's. |
| 7 | Burnt LEDs unreported | The resistor rule (`lampLegs`) now limits every lamp leg on a rail, per node, packing legs on different nets into an `rnet9`. It moves the leg out of the rail net rather than detaching the rail, fixing a second bug: the rest of a named `GND` net was hung off the resistor. `burntLamps` reports what is left (`LED_BURNS`) at L5 and in every test state. The audit's `DECODER_SPEC` fixture had been burning all eight LEDs. |
| 8 | `io` contention unchecked | Every test state is now checked for shorts, conflicts, oscillation and burns, not just the default state. `io` pins remain the engine's to judge. |
| 9 | Faults named `c2` and raw net ids | Faults use spec ids and declared net names (`partNamer`, `electricalNamer`). An oscillation names its nets. An `X` net is `NET_UNRESOLVED`, not "nothing drives it". A bus with every enable off gets bus advice, not "tie it to GND". The repair message now also lists the compiler's `RESISTOR_INSERTED` and `PULL_INSERTED` notes. |
| 10 | ROM contents cannot be specified | Not added. It would be a feature (a schema field plus byte programming). Instead the compiler warns `ROM_UNPROGRAMMED` to the user, and the prompt says a ROM arrives empty. |

**Loud issues:**

- **Tri-state buses** are allowed. Outputs may share a net when all of them can be switched off, which `switchableOutputs` probes from the evaluator.
- **Memory enables.** `outputEnables(def)` (`catalog/index.js`) reads a memory's `ceN`/`oeN` off its own `logic.memory`. That gives memory CE/OE the `!` mark and the `OUTPUTS_DISABLED` diagnosis, and it lets two ROMs share a bus.
- **Oscillators** are no longer offered to the builder (`BUILDABLE_DEFS`).
- **Prompt wording.** The prompt no longer claims a bare `led` or `resistor` cannot be used. The card legend now covers power pins and other passive pins, and parts list their `buses`.
- **Test pin grammar.** `expect` pins resolve through `resolvePin`.
- **Stale test reference.** The comment pointing at `tests/catalog-brief.test.js` now points at `tests/ai-generate.test.js`.

**Still open.**

- The tests are written by the same model that wrote the circuit. A misunderstanding shared by both still passes L7. The suite rules make that harder but cannot rule it out.
- Memory contents in a generated design.
